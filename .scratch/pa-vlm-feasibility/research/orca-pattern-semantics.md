## Finding

The feasibility experiment can assume OrcaSlicer 2.3+ batch PA Pattern outputs one physical test per configured speed/acceleration pair, with tests potentially spread across plates. It cannot assume one universal plate layout or exact print geometry: the printer, nozzle, pattern range/step, speed and acceleration settings affect it. For this target, each physical pattern is a herringbone-style PA sweep, and the user-configured PA range/step define its candidate values. OrcaSlicer recommends a 0.001 PA step for meaningful distinctions, but this is a recommendation, not a guaranteed default or invariant.

## Primary-source evidence

- The [Adaptive Pressure Advance guide](https://www.orcaslicer.com/wiki/calibration/adaptive_pressure_advance_calib) says that 2.2.0+ prints the test parameters needed for the adaptive table on the sample, with a documented example of acceleration 12000 mm/s² and flow 27.13 mm³/s. It describes the relevant test regions as herringbone patterns, recommends PA step 0.001, and says OrcaSlicer 2.3+ batch mode generates a test for each configured acceleration/speed pair, with parameters set accordingly. Its result table gives flow in mm³/s, acceleration in mm/s², and triplets in PA, flow, acceleration order.
- The [Pressure Advance guide](https://www.orcaslicer.com/wiki/calibration/pressure_advance_calib) says the pattern method is adapted from Andrew Ellis's generator, itself derived from the Marlin pattern method. It says a test is represented in the plate as a small rectangular-prism handle while the calibration pattern is custom G-code emitted at each layer; each test object has target parameters reflected in its object name. Multiple tests can be arranged on a plate, with extra plates added if needed. The pattern uses custom-drawn details beneath the numbers, not normal slicer infill.
- The [Adaptive PA profile documentation](https://github.com/OrcaSlicer/OrcaSlicer/wiki/material_flow_ratio_and_pressure_advance) specifies the output data contract: numeric rows are PA, volumetric flow, acceleration, separated by commas. It also warns that slower/lower-acceleration tests can have a wider acceptable PA interval, and recommends taking the faster test's value when no visual difference is visible.
- Generator source is in OrcaSlicer's [`src/libslic3r/calib.cpp`](https://github.com/OrcaSlicer/OrcaSlicer/blob/main/src/libslic3r/calib.cpp) and declarations/defaults in [`src/libslic3r/calib.hpp`](https://github.com/OrcaSlicer/OrcaSlicer/blob/main/src/libslic3r/calib.hpp). The source defines the generated pattern and drawing/label routines; the documentation remains the clearest user-facing source for supported version semantics and the batch layout contract. `CalibUtils.cpp` invokes `CalibPressureAdvancePattern` and places it based on the generated print dimensions ([upstream source](https://github.com/OrcaSlicer/OrcaSlicer/blob/main/src/slic3r/Utils/CalibUtils.cpp)).
- A follow-up source check found that the PA Pattern generator [draws a number at every other candidate index](https://github.com/OrcaSlicer/OrcaSlicer/blob/main/src/libslic3r/calib.cpp) while [assigning `start + index × step` to every candidate line](https://github.com/OrcaSlicer/OrcaSlicer/blob/main/src/libslic3r/calib.cpp). A value between adjacent printed numbers can therefore belong to a real unlabelled line. For this batch, the user confirms that line mapping and the preferred values; project or G-code files are optional cross-checks if the markings conflict.

## What the prototype may safely rely on

- Detect and parse PA labels only when visibly readable; candidate PA values are a configured range/step, not values a VLM should invent. Current generator source prints only alternate candidate values, so an unlabelled physical line can be mapped from readable anchor labels and physical line order. The user's confirmed triplets provide an independent reference for testing that mapping.
- Treat flow and acceleration as printed metadata for 2.2+, but independently verify recognition and units. For 2.3+ batches, expect one pattern per configured speed/acceleration pair; do not use plate position as identity. Use the visible markings plus independent configuration/G-code/3MF provenance when available.
- Preserve full precision from readable labels/configuration. The docs recommend PA step 0.001 but allow it to be increased to reduce test size; adjacent values may therefore differ by other increments.
- Interpret flow as volumetric flow in mm³/s and acceleration in mm/s². Speed is an input/proxy used to produce target flow; actual flow can depend on layer height, line width, extrusion limits, and whether the toolhead reaches requested speed. The docs caution that short pattern segments can prevent the actual flow reaching the nominal target, especially at high speed and low acceleration.
- Export the settings tuple in the documented order `PA,FLOW,ACCELERATION`; the PA is the selected calibration result, not a label-derived metadata field.

## Must be confirmed on the user's actual prints

1. Visible PA anchors, the intervening physical lines, and their ordering; use the user's confirmed mapping for this batch and consult the exact OrcaSlicer build/configuration only if a conflict appears.
2. Physical label legibility, label-to-test-line mapping, print orientation, raster features, and whether labels survive the chosen camera distance, lighting, filament color, first-layer condition, and print quality.
3. Actual printed metadata values and units against the user's confirmed triplets. The guide's examples establish nominal semantics, not successful OCR on this printer; slicer files are optional cross-checks for conflicting markings.
4. Whether each requested speed/acceleration pair produced a distinct pattern, how patterns are assigned to plates, and whether object ordering/name/metadata reliably identifies them.
5. Whether nominal speed maps to the expected actual volumetric flow on this printer/material/nozzle; do not derive flow from a generic formula alone when Orca's printed value or G-code can be checked.
6. Which candidates are acceptable on the physical specimen, including any broad/ambiguous acceptable range. Orca's documentation does not define objective image thresholds for corner quality; independent expert inspection of the actual print is required as ground truth.

## Scope note

The official user documentation is explicit about 2.2+ metadata marks and 2.3+ batching. The current generator source clarifies the alternate-line numbering rule; the documentation does not guarantee optical readability or that the user's actual batch uses the same settings and layout. Those are feasibility-dataset questions. PA interpretation also depends on printer/filament/profile conditions and print quality; metadata recognition alone cannot validate the print or determine a preferred PA.
